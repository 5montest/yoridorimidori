## 1. 実装した内容

### フェーズ1（P0）: 安全側の状態遷移

| 変更 | 内容 |
|---|---|
| **到着判定の品質ゲート** | 到着は「距離 < 10m」に加え、**GPS 精度が good/fair**・**測位時刻と受信時刻の差 ≤ 5 秒**・**位置鮮度が lost/stale でない**を満たす場合のみ確定。古い測位・低精度測位で「到着」にしない。 |
| **位置ロストを到着より先に判定** | `locationFreshness === 'lost'` または位置フィルタ unavailable のときは、距離 < 10m でも `position-lost`。 |
| **方位ロストで案内しない** | `headingFreshness === 'lost'` または方位フィルタ unavailable のときは `heading-unknown`（相対方位 null）。古い方位で通常案内を続けない。 |
| **案内表示の信頼度** | `NavState` に `guidanceAvailability: 'normal' | 'hold' | 'unavailable'` と `guidanceIssue: 'position' | 'heading' | 'both' | null` を追加。 |
| **hold の条件（仮説値）** | 位置 stale、方位 stale、GPS 精度 poor/unknown、方位精度 0/1/unknown、フィルタの一時保持、目的地が近く精度誤差の影響が大きい（`distance < accuracy × 3`）。 |
| **鳥の表示** | `hold`/`unavailable` では**前回の向きを保持**し、回転を更新しない（不確かな方位で誤誘導しない。0° に戻さない）。`hold` は不透明度 0.7、`unavailable` は 0.45。 |
| **文言** | `hold`: 「目的地は 右（確認中）」など、`unavailable`: 要因別に「現在地を確認しています…」「方位を確認しています…」「現在地と方位を確認しています…」。 |

### フェーズ2（P1）: 円周型の平滑化＋状態遷移

| 新規ファイル | 内容 |
|---|---|
| `domain/headingFilter.ts` | 円周対応の指数移動平均（`1 - exp(-dt/τ)`、τ=500ms）。大ジャンプ（45°超・800ms 以内）は一時保持し、同じ新しい向きが 3 回続いたら実回転として採用。低精度（0/1/null）は保持し、3 秒超で unavailable。真北⇔磁北の基準変更で再初期化。unavailable からは 3 回連続妥当で復帰（ヒステリシス）。 |
| `domain/locationFilter.ts` | 精度 30m 超は保持。位置飛びは `max(200m, (前回精度+今回精度)×4)` を超えたら一時保持し、同じ位置が 2 回続いたら実移動として採用（**速度による一律判定はしない**＝電車移動を許容）。精度×0.5 未満の微小移動は前回位置を維持しつつ受信時刻を更新。 |
| `domain/signalQuality.ts` | `SignalMode` / `SampleDecision` / `SignalQuality` / `SignalReason`（開発ログ用の理由コード）。 |
| **配線** | `useNavApp` で位置・方位の受信時にフィルタを適用し、`sensor/location` / `sensor/heading` には採用値のみを流す。`signal/quality` アクションで品質と判断履歴（最大 20 件）を reducer に保持。Mock 切替・シナリオ切替・購読再開でフィルタを初期化。 |
| **開発メニュー** | 「信号品質（方位・位置）」カードを追加。最新の mode/decision/reason と直近 5 件の判断履歴を表示（通常画面には出さない）。 |
| **Mock シナリオ** | 検証用に 6 件追加: 方位ジッター（±20°）/ 方位ジャンプ（180°）/ 方位 0° またぎ（350→10）/ GPS 位置飛び（500m）/ 電車移動（20m/s）/ 方位精度の劣化（3→1→0→不明）。合計 12 シナリオ。 |

### フェーズ3（未実装・設計メモ）

ジャイロ統合（`expo-sensors` の Gyroscope / DeviceMotion 等）による相補フィルタは**実装していない**。理由:

- SDK 58 の `expo-sensors` API（利用可能センサー・レート・Android のバックグラウンド挙動）を一次情報と実機で確認していない。指示書 §0-8 の「未確認 API を推測で実装しない」に従う。
- トンネル内の磁気外乱に対する改善は、まず「誤誘導しない（hold/unavailable）」ことで安全側に倒す設計を優先した。
- 次段階の設計案: ジャイロの角速度を短期積分し、磁気方位を長期補正に使う相補フィルタ。磁気異常検出時はジャイロのみで保持し、一定時間で unavailable。実装前に `expo-sensors` の API 検証・Mock 注入・実機ログ取得が必要。

## 4. 追加修正（2026-11-03）: GPS 途絶後の「移動しながらの再取得」

### 発見した不具合
`locationFilter` の位置飛び復帰条件が「**同じ新しい位置が N 回続く**」ことだったため、
電車のように **GPS 途絶中に移動して復帰後に毎回 20m ずつ位置が変わる**ケースでは、
候補位置が毎回変わり `consecutiveRejected` がリセットされ続け、**新しい位置を永久に採用できない**
（古い位置を保持し続ける）可能性があった。

- 再現テストを先に作成（`locationFilter.test.ts` の「GPS 途絶後の移動再取得（電車）」4 件）。
  - 30 秒途絶・600m 移動後、1 秒ごとに +20m の位置 → **修正前は `acceptedFix === null` のまま失敗**（再現）。
  - 短い途絶直後の 500m 飛びは保持（安全側）されること。
  - 短い途絶後に移動を続けた場合は数回で復帰すること。
  - 途絶後に元の位置に戻った場合は誤検出しないこと。
- 修正前のテスト結果: 3 件失敗（不具合を再現）。

### 修正内容（`domain/locationFilter.ts`）
1. **時間ベースのジャンプ許容量**: `allowedJump = max(200m, (前回精度+今回精度)×4, 経過秒 × 90m/s + 精度×2)`。
   長い GPS 途絶の後は移動している可能性があるため、想定最大速度（90m/s ≒ 324km/h・電車想定）までは
   実移動として受け入れる。
2. **移動しながらの復帰判定**: 候補は「直前の棄却サンプル」に毎回更新し、連続サンプル間の距離が
   `max(精度×2, 経過秒 × 90m/s × 1.5, 10m)` 以内なら「整合する移動」とみなして `recoverySamples` 回で採用する。
   - 同一地点に留まる誤測位だけでなく、電車の連続移動でも復帰できる。
   - ランダムに飛び続ける GPS（毎回 500m 等）は距離が許容を超えるため採用しない。
3. 設定値を `LocationFilterConfig` に追加: `maxPlausibleSpeedMps`（90）、`candidateToleranceFactor`（1.5）。
   状態に `candidateAtMonotonicMs` を追加。
